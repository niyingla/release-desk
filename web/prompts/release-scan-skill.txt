# 扫描版本并写入 Release Desk

把有来源证据的版本事项填入软件的本地 JSON，由软件自动刷新。用户的生成请求已经授权写入版本记录，不再请求一次保存确认。类型包含 job/config/sql/topic/init_api/verify；扫描仅记录初始化接口，不实际调用。

## 确定输入

- 默认数据根目录为当前用户 `%APPDATA%\ReleaseDesk`；用户指定 `--data-dir` 或目录时以指定值为准。
- 读取该目录 `settings.json` 的 `code_repository`、`sql_repository`、`git_author`。不在技能里固定仓库绝对路径，不读取 `connection.json`、登录凭据或环境密钥。
- 版本优先取用户明确版本号，否则从代码仓库当前发布分支推导。仍无法确定才询问，不用 Maven 日期版本号。
- 默认只整理设置中的作者（以当前软件设置为准）。用户明确说“全团队”时扩大代码范围；SQL 作者按用户本次指令，否则沿用配置。
- 若存在，先读取 `AI模板\AI填写说明.txt`、`AI模板\版本记录模板.json` 和 `版本文件\{版本}.json`，遵循软件协议。

## 只扫描真实有效改动

1. 查看 Git 当前分支、HEAD、已有发布分支或 tag、工作区状态；用 Git 对象读取指定版本，不能把其他开发分支或未提交改动当作已发布内容。
2. 选取有实际发布依据的旧版基线，对照发布净 diff 和目标作者的非合并提交；上次扫描、同版本中间提交及来源父提交不自动代表已上线旧版。核对撤销、冲突清理、已在 hotfix 上线的相同改动；不要把整个合并提交里的其他作者代码都归给当前作者。
3. 已有发版说明、问题验收记录可以作为线索，但必须回到目标分支源码/提交核实。记录基线、HEAD、作者和来源；本地或远端缓存 SHA 不直接当成生产部署 SHA。
4. 从源码确认新增/修改的 XXL-Job handler、实际配置项、Kafka topic/消费组。频率、分区数、生产取值没有证据就留空或写待确认，不按经验填值。Redis 延迟任务不要伪装成 XXL-Job。
5. SQL 从配置仓库的目标版本目录与指定作者提交读取完整原文，保留 `source_path`、`source_commit`、`source_author`。已在前一版本发布的脚本不重复列为本次新增。分类只解析 SQL 正文：创建表、修改表、初始化数据，绝不依据目录名；混合脚本不重排内部语句。
6. 每个有效业务改动先说明原问题、修复机制、业务目标及关键边界，再给出可选的代码/日志取证路径和源码中真实存在的关联线索。生成阶段没有查询生产，不填写预先通过或失败的结论；纯代码存在或零错误日志不能判定上线验收通过。

## 生成灵活的验证条件

### 先区分发布基线与开发演进

- 发布比较始终为“实际已发布旧行为 → 目标版本最终实现”。同一版本反复开发、提交和扫描不代表中间实现已上线；现有 JSON、source_commit、上次目标 SHA 和来源父提交仅是需求/开发线索，不能因被扫描过或有验证记录就升级成发布基线。
- 基线依据用户明确的发布事实、可核对的已发布 tag/提交或上线记录。分支名、标签名、merge-base、提交日期和软件版本状态本身不能证明具体快照已上线；依据不足时写“发布基线待确认”，列候选和限制，不能将未知当空，也不能退回上次扫描快照。仅只读本地 Git 对象与已有引用，不为扫描 fetch、pull 或切分支。
- 已发布基线没有该项能力时，本需求的旧业务行为为“无此需求/功能”，按新增业务验证最终关键目标。空的是该项需求的旧行为，不是整个仓库；已有框架、入口及其他功能仍可存在。新需求在未发布版本内的修错、重构、参数调整合并为开发演进，不另造“线上第一版有 bug”的验证项，也不要求线上出现开发第一版的行为或日志。
- 已发布旧版确实有该能力或问题时，才按线上修复/已有功能修改描述发布净差异。版本号相同也可能存在已发布中间构建，但只有明确的发布事实支持时才以它为旧版。
- 在 source_evidence 分别标明发布基线及确认依据、本轮目标 SHA、需求来源提交及开发演进。重扫/单项更新时纠正旧 change、steps、expected、keywords 中错误的“线上旧版”假设，保留稳定 ID、人工状态及历史，不改写过去的验收结论。
- 本地旧 AI填写说明或历史记录若仍要求将来源父提交、上次扫描作为线上旧版，按本节纠正；旧说明不是发布事实。

例如：5.7.0 的某新需求第一版已扫描，随后又修改，但两版都未上线；若真实已发布基线没有此需求，再扫仍是“无此需求 → 5.7.0 最终实现”，不是“5.7.0 第一版 → 第二版的线上 bug 修复”。若该需求早已存在于真实已发布旧版，则仍需比较旧版实际行为，不能因当前版本未发布就把所有需求都视为空。

- **只生成关键验证项**：围绕核心业务逻辑、新业务关键流程和实际 bug 修复，按独立业务目标合并关联提交与文件。实体/DTO/CRUD 脚手架、普通重构、注释、格式、依赖与版本号等没有独立改变关键业务行为的内容，不单独创建 verify；若确实影响重要行为，归入对应业务目标，不按文件类型机械排除。没有关键业务变化允许零项。SQL、配置、定时任务和 Topic 的发布事项仍如实记在各自清单，不另造重复的通用检查任务。
- **线上 bug 要保留发布前后对照线索**：先确认问题属于实际已发布旧版，再对照发布基线与最终目标净 diff 核实旧逻辑、新机制和关键反例。来源提交及父提交用于解释开发演进，不能单独证明线上有过该 bug。在 `change` 与 `data.source_evidence` 中分别标注发布前后 SHA/依据及开发来源、路径和方法；旧代码或发布依据不足时说明限制，不把同版未上线的新需求写成线上修复，也不声称已验证。
- **新业务只查关键流程**：参考验证方式聚焦核心入口、主要业务分支、业务结果与源码真实存在的关键日志，不逐个检查模型、CRUD、字段等技术细节，不扩展成无关模块或数据库全量巡检。生成阶段仍不查询生产，线上日志由用户后续主动验证时读取。
- **先评估日志可观察性**：每个 verify 的 `verification_mode` 填“自动验证”或“手动验证”。关键结果可由真实日志、分支或关联上下游证据判断时可自动取证；仅能人工观察页面、未记录返回值或通过主动操作确认，且没有充分替代证据时，声明手动验证，在 `manual_reason` 解释不可观察点、`steps` 写人工步骤。软件将其标为需手动验证、排至末尾且禁用自动选择。分类依据代码可观察能力，不根据某一窗口无样本判人工。自动验收允许基于确定性代码修复和相互印证的生产信号作高概率确认，不能将“未逐一复现全部罕见边界”统一设为阻塞条件。
- **以最终实现为准并区分证据强弱**：固定本轮目标 SHA，来源提交后的覆盖、撤销及其他作者补充要核对净 diff，不能把后续实现倒算给原作者。验证条件优先给出能区分修复前后的业务样本与结果，分清核心风险和可选扩展边界；附带低风险边界不统一设为阻塞条件，核心身份隔离、幂等或并发目标仍需对应证据。部署 SHA 是直接版本证据之一，不能预设为每项唯一通行证；后续可由 AI 评估可关联且能区分旧逻辑的运行行为作为间接依据，但普通 HTTP 200、入口日志、通用流程完成或字段内部一致不能自动证明修复生效。扫描阶段不查询生产，不把提交时间当作部署时间。
- `change` 写清原问题、改动机制和涉及调用链，使后续 AI 能回到对应版本代码自行判断，不只罗列文件名。
- `expected` 描述可观察的业务目标和反例，例如“同一业务日期重复请求只产生一个有效任务”，不要写成“必须命中某句成功日志才通过”。这是待验证目标，不是扫描时已确认的线上事实。
- `steps` 提供适合该改动的可选取证路径、关键风险场景及证据不足时的补查方向。允许后续 AI 根据代码和真实日志调整方案，不要求逐条机械执行，也不限定只能使用日志；并发、幂等、主从延迟等场景仅在该改动确实涉及时说明。
- `keywords` 只写源码实际存在的日志、结构化字段或业务关联线索，说明适用范围。没有专属成功日志可留空，不能编造日志、把入口命中当成业务完成，或把零命中写成失败条件。
- 后续验证先集合对应版本代码与生产日志，再由 AI 比较目标、实际实现和运行行为，自主判断通过、失败或证据不足。参考条件过时或与实现矛盾时允许有依据地调整并说明原因；日志不可得时记录缺口和尝试，不能将静态代码判断冒充线上通过。
- 更新已有记录时，可依据本次有效代码差异把过时的固定条件改写为参考线索；仍须保留稳定 ID、人工状态和历史，不批量修改无关版本。

## 文件协议

目标为 `版本文件\{版本}.json`，UTF-8。顶层 `format` 固定 `release-desk-version`，`schema` 为 1，`version` 包含 `name/status/date/notes`，`items` 为数组。

每项包含稳定且版本内唯一的 `id`、`kind`、`action`、`service`、`status`、`data`。`data` 的值全部为字符串，原文换行保留。

| kind | data 字段 |
|---|---|
| job | handler、frequency、description |
| config | filename、prefix、content、required（必须配置/可选配置/待确认）、description |
| sql | name、side（租户端/服务商端/平台端）、database、order、sql、rollback、description；phase 可省略，由软件解析 |
| topic | topic、partitions、group、description |
| init_api | name、side（租户端/服务商端/平台端）、method、service_path（Controller 服务内路径）、url（含服务前缀的网关调用路径）、parameter_mode（无参/必填参数）、params（Query JSON 模板）、body（Body JSON 模板）、prerequisites、expected、description |
| verify | title、change、verification_mode、manual_reason、steps、keywords、expected、result |

- `action` 为新增/修改/删除；定时任务 `job` 另支持“关闭”：保留定义并停用调度时用关闭，真正移除任务定义才用删除。关闭是待执行操作，不表示已关闭或已发布。待办 `status` 为待处理/进行中/已完成。版本发布 `status` 为计划中/进行中/已发布，与验收状态分开。
- 配置 `required` 依据真实配置读取及使用逻辑填写。代码默认值足以满足本次上线行为才标“可选配置”；缺配置无法正常运行或必须覆盖默认值才标“必须配置”；证据不足标“待确认”。在 description 说明默认值及代码依据；旧记录缺字段不能推断为可选。
- 在 `data.source_evidence` 写来源 SHA、路径、方法或资料位置，不把注释里的候选词写成已存在日志。
- init_api 仅从明确的上线初始化要求及真实接口代码推导，不把所有 Controller/CRUD 都归为初始化。核对网关路径、HTTP 方法、所属端、前置条件和结果判断；模板列出的字段均为必填，实际值未知时留空供用户调用前填写。软件由用户手动选测试/线上、展示地址与参数，每次输入 Authorization Bearer Token 后才发送；扫描不能调用、写入 Token 或标记调用完成。
- `com.qiyu.douyin.common.core.annotation.PostReleaseManualRun` 是上线后手动调用的明确标记，按目标 Git 快照检索其全限定写法及正确 import 的简写。重点检查 **Feign API 方法**及实现，也检查直接标注的 **Controller 运维端点**；不能因 Controller 未重复注解漏掉 Feign，也不为无 Feign 的运维入口虚构契约。`version` 非空时精确匹配本次业务发布版本（5.8.1 不匹配 5.8.10）；为空时依据本次新增/变更来源及发布范围确认，不把所有历史标记接口每版重复列入。未提交工作区标记仅作待提交提示，不能冒充固定目标中的已存在代码。
- 读取 `PostReleaseManualRun.value` 的完整执行说明（包括 Java 字符串拼接），映射到 prerequisites/description；结合 `@ApiOperation` 或方法说明生成 name。解析 `REQUEST_MAPPING` 等常量、类型和方法上的映射得出 service_path，结合已有可信网关映射得出含服务前缀的 url，核对 HTTP 方法及所属端；Feign 与 Controller 同一接口只建一条稳定 ID 记录。网关映射未确认时仍填写已知 service_path，url 留空并在 prerequisites/warnings 写明缺失信息，不将全部路径留空或把服务内路径当网关路径；保留已有且有来源的映射，注明核对环境，不能将测试配置冒充生产事实。所有服务在同一 Nacos 只说明可服务发现，不代表网关 Path 前缀可由服务名直接猜出；Token 负责登录上下文，不替代路径映射。扫描继续只读本地资料，运行配置的联网核对由用户另行授权，不能主动调用初始化来试路由。无参写“无参”；有必填 Query/Body 时根据参数注解、DTO 校验和真实默认值生成对应 JSON 模板，未知值留空，不能把选填字段误标必填。路径变量需明确指出调用前替换为实际路径。
- 标记说明包含分页/分批时，把首批参数、返回游标、下一批传参及停止条件写进 prerequisites/expected。只整理人工执行步骤，不在扫描中调用、自动翻页或初始化数据；注解不改变鉴权及实际 HTTP 成功判断。
- 没有新增定时任务、配置、SQL 或 Topic 时允许该类为零项，不为凑齐六类清单生成假记录；在版本 notes 解释范围。
- SQL 文本只进入版本 JSON，不新增或改动业务 `.sql` 文件。不要从记录触发数据库、定时任务、生产日志查询、发布、提交或推送。

## 合并和状态

- 先读现有文件，复用相同事项的稳定 ID；保留没有出现在本轮扫描中的旧记录，不能以省略表示删除。
- 保留人工归档标记 `version.archived`、上线标记/时间、待办状态、执行审计、验证历史。软件执行历史存独立文件，禁止由 AI 赋值。
- 用户确认版本已经上线时，可将版本发布状态写为已发布并记录其明确日期；不能因此把所有 SQL 标为成功或所有验证标为通过。
- 引用已有验收报告时标明报告日期、证据范围和未完成场景，不冒充本轮重新查询。证据不足仍待验证。
- 保存前备份已有 JSON；先写同目录临时文件并校验完整 JSON，再原子替换目标。不要修改软件内存数据库或凭据。
- 软件由文件监听读取更新。完成后给出目标文件路径、六类数量、基线/作者及待确认信息，不要求用户手工再次导入。

## 软件内只读扫描模式

如果调用方提供输出 Schema，并明确要求“只返回结构化结果”，执行同样的证据扫描，但不写任何软件文件、不运行数据库和外部数据源，也不复制敏感信息。按调用方结构返回候选事项，由软件负责校验、合并、备份和保存。

可用指令示例：`使用 $release-desk-version-scan 扫描 5.7.1，仅整理我的改动并写入发版软件。`
