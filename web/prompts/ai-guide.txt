Release Desk — AI 版本文件协议 v1

版本文件目录：__VERSION_DIR__
每个版本一个 UTF-8 JSON 文件。文件名必须与 version.name 一致，例如 5.7.3.json。
先读取该版本现有文件，保留稳定 id 与已有项，再合并本次变更。
软件每 2 秒检查文件；无效 JSON 不覆盖内存中的版本记录。
请先写同目录 .tmp，完成后原子替换 .json，避免软件读取半写入文件。

格式：format 固定 release-desk-version，schema 固定 1。
version.name 必填；status 为 计划中/进行中/已发布；date 格式 YYYY-MM-DD；notes 为备注。
items 每项 id 必填、稳定、同版本唯一；不能更改已有 id 的 kind。
kind 为 job/config/sql/topic/verify，展示顺序同此。
action 为 新增/修改/删除，定时任务 job 另支持“关闭”。新建任务用新增，调整已有任务的频率、参数或逻辑用修改，保留定义并停止调度用关闭；真正移除任务定义才用删除，不把关闭写成已上线状态。status 为 待处理/进行中/已完成；service 填实际服务名称。
data 的所有值为字符串，保留 SQL、配置和验证步骤的换行。

job: handler（名称）, frequency（仅 Cron 表达式，如 0 0 10 * * ?）, description（描述）。频率的中文解释由软件自动生成；源码说明、Admin 待核对等备注写入 description，不得拼入 frequency。无法确认实际 Cron 时 frequency 留空，在 description 说明依据和待确认项。
config: filename（文件名）, prefix（配置前缀）, content（完整配置）, required（是否必须配置：必须配置/可选配置/待确认）, description。
配置 required 仅在确认代码默认值足以满足本次上线行为时填写“可选配置”；须显式覆盖默认值或缺配置无法正常运行时填写“必须配置”；证据不足或旧文件缺字段填写“待确认”。在 description 写明实际默认值、代码依据及何时需要覆盖；不得仅因存在默认值就判断为可选。
sql: name, side（租户端/服务商端/平台端）, database（说明）, order（同类型内数字顺序）, sql, rollback, description。
phase 由软件解析 SQL 正文得到，不必填写；目录名、文件名和 AI 填写的类型标签不影响实际分类。
topic: topic, partitions（数字字符串）, group（消费组）, description。
verify: title, change（修改内容）, verification_mode（自动验证/手动验证）, manual_reason（需手动原因）, steps（参考验证步骤）, keywords（参考日志线索，可选）, expected（参考预期结果，可选）, result（默认留空）。
每项先评估可观察性：关键业务结果能从真实日志、分支或可关联上下游证据判断时为自动验证；只能观察页面、未记录返回值或主动测试才能确认，且没有有效替代证据时为手动验证，填写 manual_reason 和人工步骤。手动项由软件标记“需手动验证”，置于尾部，禁止自动选择；一次日志无样本不直接决定此分类。自动判断允许有依据的高概率确认，说明推断和未覆盖场景，不要求所有罕见边界逐一复现。
只对核心业务逻辑、新业务关键流程和实际 bug 修复生成验证项；同一业务目标合并关联提交与文件，不为普通实体/DTO/CRUD 脚手架、注释、格式、无行为变化的重构逐项创建任务。真正影响核心行为的改动纳入对应业务目标，不按文件类型一刀切。SQL、配置、定时任务和 Topic 的发布事项仍在各自清单记录。
bug 验证必须对比修复前后代码，记录可核对的基线/提交、旧问题和修复机制，并结合对应线上日志由 AI 分析是否生效。新业务聚焦关键逻辑与关键日志；没有拿到旧代码或日志就明确证据缺口，不编造前后差异或上线成功。
来源提交之后若有覆盖、撤销或其他作者补充，以固定目标 SHA 的最终实现为准，区分代码归因。验证条件应优先描述能区分旧问题与修复后行为的核心业务结果，把附带低风险边界列为可选观察；涉及核心身份隔离、幂等或并发时保留对应关键场景。部署 SHA 不是所有事项唯一的版本证明，可由后续 AI 评估可关联、能区分旧逻辑的生产行为作为间接依据；HTTP 200、入口命中或普通流程完成不能单独证明目标已实现。生成阶段不查询生产、不预设结论。
生成验证记录时，change 说明原问题、修复机制和关键边界；expected 写可观察的业务目标与反例，不把某句日志设成唯一通过条件。steps 给出可选取证路径、风险场景及补证方向，keywords 只填真实源码中的日志或关联线索，没有专属日志可留空。以上均为待验证假设，实际验证由 AI 结合对应版本代码和生产日志自主调整方法并判断；扫描阶段不得把参考条件写成已经验证的事实。

SQL 使用库内语句，不写 USE、数据库名前缀、DELIMITER、全局配置或动态 SQL。
AI 只新增/更新；从文件移除一项不会删除软件记录，删除使用软件按钮。
人工维护的上线状态、待办状态、验证历史会保留。
修改验证条件后当前验收状态重置，历史结论继续保留。
AI 不得编造代码变更、上线结果或日志证据。
SQL 执行审计由软件维护，不通过版本文件赋值或触发。
禁止把密码、token、手机号写进版本文件；禁止读取 connection.json。

给 Codex 的参考指令：
“阅读本说明与模板，根据当前发布版本真实 Git 改动，更新目标目录的版本 JSON。
保留已有记录 ID，补充五类事项及上线后的日志验证方式。
只写有证据的内容，不执行数据库、不发布，不把模板示例原样导入。”

Codex 验证：软件复用本机已登录账号，先集合对应版本的代码改动与生产日志，再综合判断业务目标是否达成。服务、验证方式、关键词与预期结果仅为参考，缺少时仍会分析，不按固定关键词或步骤机械判定。日志未命中时可调整检索路径；无法取得日志时明确查询尝试与缺口，不虚构日志事实。结果分别说明目标、代码判断、日志发现及综合理由。
用户选择时间范围并主动触发，可能消耗 Codex 额度。
结果区分通过、失败和证据不足；没有专属日志时可选其他可靠证据，区分代码层面已修复与生产已生效，不能仅凭本地代码或零错误日志判定上线通过。
